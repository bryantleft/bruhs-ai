# Project API client

Files → API lets a project send HTTP requests and GraphQL JSON POSTs through the companion server, inspect a response, import a curl command, and save requests plus one working environment as a plain-text collection in the repository. Web and native desktop use the same host and models.

The first version supports method, URL, literal headers, raw/JSON body, ordinary environment variables and named keychain references. It imports one curl request with a strict set of nonexecuting flags, preserving curl’s implicit form content type and explicit JSON header overrides ([curl manual](https://curl.se/docs/manpage.html#--data)). Multipart file reads, OAuth setup, protocol streams, OpenAPI import, request scripts and automatic response chaining remain outside this ticket's first delivery.

Saved requests use `.bruhs/api/collection.json` under the exact canonical working folder. The host checks the path, refuses symlink components, and saves with an atomic replacement and a content revision check so edits observed before the save are reported as conflicts. In the normal UI/MCP path, only owner controls save or change the collection and its environment; agents propose a request in memory. A revision conflict retains the user draft and requires reload/review before saving again. The collection contains ordinary environment values and credential names, never resolved keychain values. Save sensitive values with the private credential form in Files → API, because ordinary variables are plain repository content. Authorization, Cookie, API-key/token/secret-named headers require a keychain variable rather than a literal saved token.

The native SecretStore resolves references only while sending. A new credential value exists transiently in the masked Files → API form, travels in a private same-origin request to the companion server, and is cleared after saving; Settings → Credentials manages saved names and replacements. This client never reads values back into a form. The HTTP client disables redirects, system proxies, cookie storage, automatic retries and Referer, rejects URL credentials and transport-control headers such as Host, Content-Length, Connection and Proxy-Authorization, and excludes Bruhs' configured private server ports/origins and known portless app aliases. Redirects are displayed for manual review. Credentials referenced by the current request, in raw, JSON-escaped, percent-encoded and Base64 forms, are redacted from response text and header names/values before they leave the native secret module. Sensitive response headers are also redacted. Arbitrary server transformations of a secret cannot be recognized as a secret.

One active send is permitted across the companion server at a time. The 10-second budget leaves half the native caller's existing 20-second budget for response delivery. The request specification plus environment and the response JSON each fit 32 KiB; expanded URL text and expanded headers/body have their own 32 KiB checks. The final encoded MCP envelope is also checked against 64 KiB because escaping can expand it; an oversized tool result directs the owner to Files → API or a narrower endpoint response. Oversized HTTP responses fail rather than return a partially redacted body. Cancel drops the in-flight future. It cannot undo a remote write that has already reached its server. User-originated responses live in panel state until an explicit attachment to the current unsent draft. Approved agent-request results are readable only by that originating project and turn. Neither path keeps persistent response history. One in-memory working-folder draft, including its last response and original collection revision, survives visiting Files and reopening API. Private credential entry is excluded. Leaving API or changing projects cancels active sends, and another project never restores the former project’s data.

Agent tools can propose an immutable request/environment snapshot and read its status/result. They cannot approve or directly send a request. The owner sees the normalized destination and payload after ordinary variable substitution, with visible keychain reference labels, before choosing Send once or Decline. Invisible formatting controls are escaped in that review. Keychain values remain hidden and use the value currently saved under the reviewed credential name when approved execution begins. Approval consumes the exact proposal once before execution, including on error; retry requires a new approval. Results are then available to the proposing turn. The proposal scope comes from the host-injected working folder and turn identity, not model arguments. Pending approvals and results are bounded private memory and are cleared on companion-server restart. The host retains at most 50 in-memory proposal/status records, reusing the existing history-page count. A new proposal automatically evicts an older terminal record when full. Pending/running records are retained; a full nonterminal queue rejects new proposals actionably.

This is a local working-tree delivery, not a published release. Host/Origin guards are the existing [local server boundary](local-server-access.md). The proposal-only MCP catalog and scoped status reads constrain this feature's normal agent tool path. They do not authenticate owner HTTP controls against arbitrary code already running under the same OS account. An approved endpoint receives its referenced credential; redaction cannot recognize arbitrary transformed reflections.

The repository collection is plain JSON. Unix directory handles plus no-follow opens keep saves within the opened project directory even when path components are replaced. Cross-process locking serializes cooperating saves, and the content hash detects external changes observed before replacement. This is not an atomic compare-and-swap against an editor that ignores that lock. A private `.collection.lock` file beside the JSON is runtime coordination, not collection content; it can remain untracked.

The application WASM browser fixture passes 49 checks at 640×480 and touch 390×844 with mocked APIs. Separate Rust tests use real local HTTP fixtures: 11 core checks cover secret reflection (including header names), redirects, cancellation before/during send, one-use/concurrent/aborted approvals, scope, payload/frame limits, curl content types and collection conflicts/symlinks; four model checks cover literal curl import and header semantics, JSON tree paths and approval review. The desktop HTTP caller and actual built server’s stdio MCP helper pass together, and a separate GPUI control harness passes. Neither the browser mocks nor the native control harness is a launched desktop integration session. Secret tests use the isolated in-memory adapter; they do not prove an actual OS keychain prompt/write. No user credential, endpoint, or collection was used.

Reproduce from the repository root:

```sh
CARGO_INCREMENTAL=0 cargo test -p bruhs-models api_client --locked
CARGO_INCREMENTAL=0 cargo test -p bruhs-core api_client --locked
CARGO_INCREMENTAL=0 cargo test -p bruhs-desktop api_client_native_controls --locked
CARGO_INCREMENTAL=0 cargo build -p bruhs-server --locked
BRUHS_API_MCP_EXECUTABLE="$PWD/target/debug/bruhs-server" CARGO_INCREMENTAL=0 cargo test -p bruhs-server api_client_native_http --locked -- --nocapture
```

The server test without `BRUHS_API_MCP_EXECUTABLE` exercises HTTP but skips the external stdio helper. For the browser check, build from `bruhs-web` with `CARGO_INCREMENTAL=0 env -u NO_COLOR trunk build --dist ../target/api-client-ui-dist`, then run `node bruhs-web/tests/api_client_browser.mjs` from the root. It requires Playwright and compatible Chromium; set `BRUHS_CHROME` to the browser executable if needed. The saved [validation receipt](../bench/api-client/results/2026-11-13/validation.json) identifies the tested source hashes and separate evidence layers.
